# AI Physician's Assistant - Architecture Overview

This document outlines the architecture of the AI Physician's Assistant, a frontend application designed to aid clinic physicians.

## Architecture Core: Single LLM with Tool Orchestration

This application leverages a **single Large Language Model (LLM)** as the central intelligence. This LLM is responsible for understanding user queries, maintaining conversational context, and intelligently deciding when and how to interact with various **custom tools** and **built-in tools** (functions) to perform specific tasks.

### Key Concepts Demonstrated
1.  **Tools**:
    *   **Custom Tools**: `updatePatientRecord`, `sendPrescription`, `sendPatientEmail`, `searchMedicineDatabase`, `saveInsight`, `retrieveInsights`. These tools allow the LLM to interact with the application's data layer (IndexedDB) and simulate external actions.
    *   **Built-in Tools**: Google Search is integrated to provide the LLM with access to up-to-date external information beyond its training data.
2.  **Sessions & Memory**:
    *   **Sessions & state management**: The `ChatInterface` component manages the active conversation session, passing chat history and current patient context to the LLM.
    *   **Long-term memory**: A simulated long-term memory is implemented via `saveInsight` and `retrieveInsights` tools, persisting key information in IndexedDB's `insights` store. This allows the AI to recall relevant data across different interactions or patient consultations.
3.  **Observability**:
    *   **Logging**: Structured logging is implemented using `dbService.log`, capturing application events and AI interactions (user messages, AI responses, tool calls/results, errors) into an IndexedDB `logs` store. This provides a clear audit trail for debugging and monitoring.

### Key Concepts Demonstrated
1.  **Tools**:
    *   **Custom Tools**:
        *   `updatePatientRecord`: Updates a patient's medical history by adding new ailments or medications.
        *   `sendPrescription`: Simulates sending a prescription to a pharmacy.
        *   `sendPatientEmail`: Simulates sending an email summary to the patient.
        *   `searchMedicineDatabase`: Queries a local mock database of medicines for drug information.
        *   `saveInsight`: Stores important information or insights into a simulated long-term memory.
        *   `retrieveInsights`: Recalls previously saved insights from long-term memory.
    *   **Built-in Tools**: Google Search is integrated, allowing the LLM to access up-to-date information from the web. The application extracts and displays source URLs from search results.
2.  **Sessions & Memory**:
    *   **Sessions & state management**: The `ChatInterface` component maintains the conversational state and patient context within the browser's React state, providing a continuous interaction experience for the active patient.
    *   **Long-term memory**: A persistent long-term memory feature is implemented using IndexedDB. The `saveInsight` and `retrieveInsights` tools allow the AI to store and recall general or patient-specific medical knowledge, best practices, or recurring patterns across different sessions.
3.  **Observability**:
    *   **Logging**: Structured logging is implemented through the `dbService.log` function, which records critical application events and AI interactions (user inputs, AI responses, tool calls and their results, system notifications like toasts, and errors) to a dedicated `logs` object store within IndexedDB. This provides an internal, persistent audit trail for monitoring application behavior and debugging.

## Data Persistence Layer

The application utilizes **IndexedDB** as a local, client-side database. This provides:
*   **Persistent Storage**: Patient data, medicine information, long-term insights, and application logs are stored locally in the browser and persist across sessions.
*   **Structured Data Management**: Dedicated object stores (`patients`, `medicines`, `insights`, `logs`) are used to manage different types of data, with defined schemas and indices for efficient retrieval.

## Interaction Flow

1.  **Patient Selection**: The user selects a patient from the `Sidebar`.
2.  **Initial Context**: The `ChatInterface` loads the selected patient's data from IndexedDB and generates an initial summary using the LLM.
3.  **Chat Interaction**: The physician sends messages to the LLM.
4.  **Tool Orchestration**: Based on the physician's query and the current patient context, the LLM decides whether to respond directly or invoke one or more of its available tools (custom or built-in).
5.  **Tool Execution**: If a tool is invoked, the `ChatInterface` executes the corresponding JavaScript function.
6.  **State Updates & Feedback**: Tool results (e.g., updated patient records, medicine search results, saved insights) are reflected in the UI, persisted to IndexedDB, and communicated back to the LLM to update its context. User-friendly toasts provide immediate feedback for tool actions.
7.  **Response Generation**: The LLM generates a natural language response, which may include displaying grounding URLs from Google Search or acknowledging tool execution.
8.  **Consultation Summary**: At any point, the physician can request a SOAP note summary of the ongoing conversation.

This architecture ensures a responsive, interactive, and data-persistent experience for physicians, augmenting their workflow with AI assistance and local data management.
